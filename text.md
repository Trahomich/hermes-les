

# Hermes LES

Пару месяцев назад я рассказывал вам про OpenClaw — современный подход к работе с ИИ. Программисты уже вовсю используют Claude в режиме агента, запущенного прямо на рабочей машине. По сути, это claw-агент на вашем ноутбуке — удобно, но не без проблем. Главная из них — безопасность.

С тех пор мы искали способ дать вам безопасного агента для рабочих задач. Эксперимент с AnythingLLM оказался неудачным: платформа заточена под другое, а про безопасность там и говорить особо не о чём.

Корень проблемы в том, что все claw-агенты работают через мессенджеры. А мессенджер — это как минимум дыра в безопасности.

Что удалось сделать: я соединил Hermes и Open WebUI. Интерфейс вам знаком — вы давно пользуетесь им для доступа к ИИ. Но теперь за привычным веб-интерфейсом стоит не просто модель, а полноценный помощник, который может действовать своими цифровыми руками.

---

## Что такое Hermes Agent

Hermes Agent — open-source AI-агентный фреймворк от Nous Research. Относится к той же категории, что и Claude Code (Anthropic), Codex (OpenAI) и OpenClaw — автономные агенты, которые используют tool calling для взаимодействия с системой.

Hermes работает с любым LLM-провайдером (OpenRouter, Anthropic, OpenAI, DeepSeek, локальные модели, 15+ других) и запускается на Linux, macOS и WSL.

## Ключевые особенности

- **Self-improving через навыки (skills)** — Hermes учится на опыте, сохраняя повторяющиеся процедуры как навыки. Навыки накапливаются и загружаются в будущие сессии.
- **Персистентная память между сессиями** — помнит предпочтения пользователя, детали окружения и уроки. Плагинные бэкенды памяти (встроенный, Honcho, Mem0).
- **Расширяемость** — плагины, MCP-серверы, кастомные инструменты, webhook-триггеры, cron-планирование, полный доступ к Python-экосистеме.

## Основные функции

### Инструменты (toolsets)

Hermes умеет искать информацию в вебе, управлять браузером, выполнять команды в терминале, читать и писать файлы, запускать Python-код в песочнице, анализировать изображения и генерировать новые. Он может делегировать задачи субагентам, планировать работу по расписанию, помнить контекст между сессиями, накапливать навыки, искать по прошлым разговорам и вести список задач.

### Делегирование (delegate_task)
Синхронный запуск субагентов — родитель ждёт завершения дочернего агента. Изолированный контекст и терминал. Поддержка batch-режима (до 3 параллельных задач). Роли: leaf (не может делегировать дальше) и orchestrator (может порождать своих воркеров).

### Cron-задачи
Долговременный планировщик. Поддерживает расписания: длительность ("30m", "2h"), cron-выражения ("0 9 * * *"), ISO-теги. Per-job: модель/провайдер, скрипт (pre-run сбор данных), контекст от других задач.

### Kanban
Долговременная SQLite-доска для мульти-профильной / мульти-воркерной координации. Диспетчер запускает воркеров, те получают фокусированный набор kanban-инструментов.

## Мультиагентность в Hermes

Hermes — не просто одиночный чат-бот. Это полноценная мультиагентная система, где задачи могут распараллеливаться между несколькими автономными агентами. Два основных механизма: делегирование (delegate_task) и Kanban-оркестрация.

### Модель взаимодействия

```
Пользователь
    │
    ▼
┌─────────┐
│ Hermes  │ ← основной агент (gateway-сессия)
│ (main)  │
└────┬────┘
     │
     ├─ delegate_task ──→ [Субагент 1] → результат
     ├─ delegate_task ──→ [Субагент 2] → результат
     └─ delegate_task ──→ [Субагент 3] → результат
```

**delegate_task** — синхронное делегирование. Родитель запускает дочернего агента в изолированном контексте со своим терминалом и набором инструментов. Поддерживает batch-режим: до 3 параллельных задач одновременно. Роли:
- **leaf** — исполнитель, не может порождать субагентов дальше
- **orchestrator** — координатор, может делегировать задачи своим воркерам (глубина вложенности настраивается)

Родитель получает только финальный summary от каждого субагента — промежуточные tool-вызовы не засоряют контекст.

### Kanban-оркестрация

Kanban — это более масштабный подход к мультиагентности. Вместо синхронного делегирования внутри одной сессии, Kanban позволяет координировать долговременные рабочие процессы между несколькими профилями Hermes.

#### Как устроен Kanban

```
┌──────────────────────────────────────────┐
│            Kanban Board (SQLite)         │
│                                          │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ │
│ │  Backlog  │ │ In Prog  │ │  Done    │ │
│ │          │ │          │ │          │ │
│ │ task-1   │ │ task-3   │ │ task-5   │ │
│ │ task-2   │ │ task-4   │ │ task-6   │ │
│ │ task-7   │ │          │ │          │ │
│ └──────────┘ └──────────┘ └──────────┘ │
│                                          │
│  lanes: идеи → backlog → todo → done     │
└──────┬───────────┬───────────┬──────────┘
       │           │           │
       ▼           ▼           ▼
  ┌─────────┐ ┌─────────┐ ┌─────────┐
  │Worker A │ │Worker B │ │Worker C │
  │(profile │ │(profile │ │(profile │
  │ alpha)  │ │ beta)   │ │ gamma)  │
  └─────────┘ └─────────┘ └─────────┘
```

#### Компоненты Kanban

1. **Доска (Board)** — SQLite-хранилище с колонками (lanes). Типичный flow: идеи → backlog → todo → in_progress → review → done. Каждая задача — карточка с описанием, приоритетом, метаданными.

2. **Диспетчер (Orchestrator)** — отдельный профиль Hermes, который:
   - Разбивает входящую задачу на подзадачи
   - Создаёт карточки на доске
   - Назначает воркеров (или воркеры сами берут задачи)
   - Отслеживает прогресс и обрабатывает результаты

3. **Воркеры (Workers)** — профили Hermes, запускаемые по расписанию (cron) или по событию. Каждый воркер:
   - Забирает задачу из lanes (in_progress)
   - Получает фокусированный набор kanban-инструментов (kanban_take, kanban_done, kanban_comment)
   - Выполняет работу в своём изолированном контексте
   - Двигает карточку по доске (done → review)
   - Прикрепляет артефакты и комментарии

#### Workflow типичной задачи

1. Пользователь ставит задачу → диспетчер декомпозирует → создаёт карточки в Backlog
2. Диспетчер двигает карточки в Todo и назначает воркеров
3. Воркер по cron забирает задачу → In Progress → выполняет → Done/Review
4. Диспетчер проверяет результат → двигает в Done или возвращает на доработку
5. Готовые артефакты собираются и доставляются пользователю

#### Преимущества Kanban перед delegate_task

| Аспект | delegate_task | Kanban |
|--------|--------------|--------|
| Масштаб | Одна сессия | Долгосрочные проекты |
| Persistence | Нет (сессия умрёт) | SQLite-доска переживает рестарты |
| Параллелизм | До 3 одновременных | Неограниченно (по кол-ву воркеров) |
| Координация | Ручная (prompt) | Автоматическая (lanes) |
| Изоляция | Контекст субагента | Полный профиль с памятью и навыками |
| Время жизни | Синхронный вызов | Дни/недели через cron |

### Gateway (мессенджеры)
Единый агент на всех платформах: Telegram, Discord, Slack, WhatsApp, Signal, Matrix, Email, SMS, Mattermost, Home Assistant, DingTalk, Feishu, WeCom, iMessage (BlueBubbles), WeChat, API Server, Webhooks. Open WebUI подключается через API Server adapter.

### Профили
Изолированные окружения: свой config.yaml, .env, навыки, сессии, память, cron. Полезно для разделения рабочих и личных контекстов.

## Аспекты безопасности

### Опасность полного доверия агенту

Доверить агенту полный контроль над системой — это как дать ключи от квартиры незнакомцу, который очень убедительно говорит, что умеет убираться. Основные риски:

1. **Непреднамеренное разрушение** — агент может удалить критичные файлы, перезаписать конфиги, запустить деструктивную команду, «помогая» выполнить задачу. LLM не понимает последствий так, как человек.

2. **Галлюцинации в командах** — агент может придумать несуществующую команду или флаг, выполнить её, и система сломается. Пример: `rm -rf /tmp/ *` вместо `rm -rf /tmp/*` — один пробел, и прощай файловая система.

3. **Утечка данных** — агент с доступом к файлам и сети может случайно отправить секреты (API-ключи, токены, пароли) в лог, в мессенджер, или на внешний endpoint.

4. **Компрометация цепочки** — в мультиагентной схеме один скомпрометированный или галлюцинирующий субагент может передать неверные данные вверх по цепочке, и все последующие агенты будут работать на основе ложных предпосылок.

5. **Саморасширение привилегий** — агент может создать cron-задачу, установить пакет, открыть порт — и всё это «для выполнения задачи», но без контроля человека.

6. **Отсутствие отката** — агент выполнил разрушительное действие? Нет кнопки «Undo». Git — частичная защита, но он не покрывает систему целиком.

### Мультиагентная схема безопасности: Надзорник (Supervisor)

Ключевая идея: **не доверять агенту выполнять команды без предварительной проверки**. Проверка результата после выполнения бессмысленна — система уже сломана. Надзиратель должен перехватывать и одобрять команды ДО их выполнения.

```
Пользователь
    │
    ▼
┌──────────────┐
│  Надзиратель  │ ← Supervisor-агент (ограниченный toolset)
│  (Supervisor) │
└──────┬───────┘
       │ делегирует задачу
       ▼
┌──────────────┐
│  Исполнитель │ ← Worker-агент (полный toolset)
│  (Worker)    │
└──────┬───────┘
       │ формирует команды, НЕ выполняет
       ▼
┌──────────────┐
│  Надзиратель  │ ← проверяет команды ДО выполнения
│  (Supervisor) │    опасные — блокирует, безопасные — одобряет
└──────┬───────┘
       │
       ▼
  Одобренные команды → Исполнитель выполняет
       │
       ▼
  Результат → Пользователю
```

#### Как это работает

1. **Пользователь ставит задачу** Надзирателю (Supervisor)
2. **Надзиратель** анализирует задачу, декомпозирует, формирует инструкции для Исполнителя
3. **Исполнитель (Worker)** планирует действия, формирует список команд — но НЕ выполняет их сразу
4. **Надзиратель** проверяет каждую запланированную команду ДО выполнения:
   - Не разрушает ли команда систему? (rm -rf, DROP TABLE, форматирование диска)
   - Не утекут ли секреты (API-ключи, токены, пароли)?
   - Не выходит ли команда за рамки изначальной задачи?
   - Не является ли команда галлюцинацией (несуществующие пути, придуманные флаги)?
5. **Опасные команды** — блокируются, Надзиратель просит Исполнителя перепланировать
6. **Безопасные команды** — одобряются, Исполнитель их выполняет
7. **При сомнениях** — Надзиратель эскалирует человеку

#### Почему проверка ДО, а не ПОСЛЕ

Проверка результата после выполнения — это закрытие ворот после того как кони украли. Агент уже выполнил `rm -rf /var/lib/postgres` — система сломана, данные удалены. Супервайзер видит «результат: ошибка, база удалена» — но поздно. Поэтому контроль должен быть пре-активным: команда не выполняется, пока второй агент не подтвердит её безопасность.

#### Реализация в Hermes

В Hermes нет встроенной архитектуры «супервайзер+воркер» как отдельного режима. Но фреймворк предоставляет все примитивы, чтобы собрать такую схему:

**Встроенная защита: approvals.mode**
Минимальный уровень безопасности из коробки — `approvals.mode: smart`. Встроенная LМ-модель оценивает каждую shell-команду ДО выполнения: опасные блокирует, безопасные одобряет, сомнительные — спрашивает пользователя. Это не мультиагентная схема, а один агент с дополнительной проверкой.

**Двухагентная схема через delegate_task**
Полноценный Надзиратель собирается из двух механизмов Hermes:

1. **delegate_task с пустым toolset** — субагент-ревьюер запускается с `toolsets=[]`. У него нет терминала, файловой системы, браузера — только анализ текста. Он физически не может выполнить команду, только оценить её.

2. **Ограничение toolset'ов** — Надзиратель получает `delegation`, `file` (чтение), `skills`. Исполнитель — `terminal`, `file`, `web`, `browser`. Надзиратель не может менять систему, Исполнитель — может, но получает инструкции формировать план, а не выполнять сходу.

```
Hermes (основная сессия)
  │
  ├─ role: supervisor, toolsets: [delegation, file, skills]
  │   └─ delegate_task → Reviewer (toolsets: [])
  │        └─ Reviewer оценивает команду: ALLOW / WARN / DENY
  │
  ├─ команда ALLOW → Hermes выполняет сам
  ├─ команда WARN → спрашивает пользователя
  └─ команда DENY → блокирует, не выполняет
```

Это реализовано в навыке **command-safety-gate** — готовый паттерн двухагентной проверки команд ДО выполнения.

#### Преимущества схемы

| Аспект | Без надзора | С Надзирателем (проверка ДО) |
|--------|-------------|------------------------------|
| Разрушительные команды | Выполняются молча | Блокируются до выполнения |
| Утечка секретов | Агент может отправить ключи в чат | Надзиратель видит план и блокирует |
| Галлюцинации | Исполняются как есть | Второй агент перепроверяет план |
| Контроль | Постфактум (когда уже сломано) | Пре-активный (до выполнения) |
| Откат | Не нужен — ничего не сломано | Не нужен — ничего не сломано |
| Стоимость | Дешевле (один агент) | Дороже (два агента), но система цела |

#### Ограничения

- **Не 100% гарантия** — Надзиратель тоже LLM, тоже может галлюцинировать или пропустить угрозу
- **Двойная стоимость токенов** — два агента вместо одного
- **Задержка** — проверка плана добавляет время к каждой задаче
- **Ложные срабатывания** — Надзиратель может заблокировать корректное действие, перестраховавшись

Схема Надзирателя — это не замена человеческому контролю, а дополнительный слой защиты. Для критичных систем (production, инфраструктура) — необходимый минимум. Для экспериментов и локальной работы — опциональный.

## Где используется
Разработка ПО, исследования, системное администрирование, анализ данных, создание контента, домашняя автоматизация и любые задачи, где нужен AI-агент с персистентным контекстом и полным доступом к системе.
## Аналогия отдела: как объяснить мультиагентность

Мультиагентную систему проще всего объяснить через организационную метафору: вы — руководитель отдела, агенты — ваши подчинённые, стажёры, младшие разработчики. Вы раздаёте задачи, дирижируете процессом, и вместо одного человека с вами работают пять. Это сразу считывается как оптимизация, эффективность, рост производительности — первый вопрос «зачем нам это?» отпадает сам собой.
